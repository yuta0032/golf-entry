# 名簿の読み出しを Google の配信経路から外す（案1・中継のみ）

管理画面の一覧が出たり出なかったりする件の根本策。**まだデプロイしていません。main にも入れていません。**

## いま何が起きているか

`admin.html` → GAS の `/exec` → **302 で `script.googleusercontent.com` に転送** → 中身はそちらが返す。
GAS の実行ログは**302 を返した時点で「完了」**になるので、
「GAS は 1.6 秒で完了、ブラウザには届かない」という食い違いが起きる。

- 9/16 の実測（Mac・3秒間隔・30回）：**200 × 30、JSON × 30、中央値 1.05 秒、3秒超ゼロ**
- 責任者の 9/16 9:10 頃の実測：**9回中2回が25秒超**
- 本人の端末では Windows Chrome・LINE 内ブラウザのどちらでも `neterr` / `timeout`
- `script.googleusercontent.com` 自体には**届いている**（本人の回線で Google のページが表示された）
  → 回線のフィルタ・DNS 説は**消えた**

→ **Google 側の当たり外れ**。こちらでは直せないので、**その経路をブラウザから外す**。

## 決めたこと

**案1：Cloudflare Worker を中継にするだけ。名簿は保存しない。**

```
ブラウザ ──→ Cloudflare Worker ──→ GAS /exec ──→ googleusercontent
         (速い・安定)        (Worker が代わりに踏み、転んだら即やり直す)
```

- ブラウザは **Cloudflare としか話さない**
- Worker は転んだら**サーバ側でやり直す**（最大3本・1本8秒）
- **KV なし・押し込みなし・トリガーなし・秘密なし**
- **GAS は1文字も変えない**（＝再承認もデプロイも不要）

**名簿を Cloudflare に保存しない**ので「資料を外へ複製しない」取り決めに触れない、という判断
（責任者判断：名簿は今も Google の転送サーバと GitHub Pages のブラウザを「通過」しており、
保存しない中継は複製にあたらない）。案2（短期キャッシュ）・案3（押し込み＋KV）は採らない。

### 記録：案3を採る場合に必要だった補い

push の認証で `email` だけを見ると、**別のアプリが同じ Google アカウント向けに発行した
ID トークンでも通る**（所有者を騙して別サイトにログインさせれば取れる）。
**`aud`（Apps Script の OAuth クライアントID）も一致させる必要がある。**
今回は案3を採らないので不要だが、将来また持ち上がったときのために残す。

## Worker の仕様（`docs/cf-worker/worker.js`）

| 項目 | 決めたこと |
|---|---|
| 受ける口 | **`GET /list` のみ**。他のパス・メソッドは 404 |
| GAS へ渡すもの | **`token` または `id_token` と `t` だけ**。`action=list` は**Worker 側で固定** |
| 可否の判断 | **GAS に任せる。**Worker は幹事の userId を持たない（公開情報でも二重管理しない） |
| GAS 呼び出し | `redirect:'follow'`、**1本 14 秒**で切る（8秒では待てば返る分を捨てていたため） |
| やり直し | 失敗・非JSON・非2xx なら即やり直し。**最大3本**。1本目 → 駄目なら2本目と3本目を**同時**に出して早い方を採る（**最悪28秒**） |
| 応答 | GAS の JSON を**そのまま**返す（`{error:'forbidden'}` も素通し） |
| CORS | `https://yuta0032.github.io` と `https://liff.line.me` の**2つだけ**許可。`Vary: Origin` 付き |
| キャッシュ | `Cache-Control: no-store` |
| 設定 | `GAS_URL` のみ（秘密ではない。`index.html` にも書かれている） |

**依存なし・単一ファイル。**ダッシュボードに貼るだけで動く。`wrangler.toml` も置いてあるが、
wrangler を使う場合だけ必要。KV なし・secrets なし。

## admin.html 側（この枝で変更済み）

- 取得の順番：**`worker` → `worker` → `jsonp`（GAS 直・保険）**
- 待ち **15 / 20 / 40 秒**、fetch の回は**2本並列**（据え置き）
- 診断行に **`via=worker,worker,jsonp`** が出る
- **`WORKER_URL` が空なら、worker の回は自動で GAS 直行に落ちる。**
  Worker を止めても・作る前でも画面は死なない

headless で確認済み：
| 場面 | 結果 |
|---|---|
| `WORKER_URL` 未設定 | GAS 直行（`via=fetch`）で一覧が出る |
| Worker 設定あり・1回目で成功 | `/list?token=…` を叩き `via=worker res=ok` |
| Worker が落ちる→2回目で成功 | `via=worker,worker res=ok` |
| Worker が2回だめ | 3本目で GAS 直の JSONP → `via=worker,worker,jsonp` |

## デプロイ後にやる検証

1. **Worker が生きているか**
   `curl -s -o /dev/null -w '%{http_code}\n' '<WORKER>/list'` → **400**（`no token`）
   `curl -s -o /dev/null -w '%{http_code}\n' '<WORKER>/'` → **404**
2. **中継が通るか**（ダミーなので `forbidden` が返れば十分）
   `curl -s '<WORKER>/list?token=dummy'` → `{"v":55,"error":"forbidden"}`
3. **CORS**
   `curl -s -D - -o /dev/null -H 'Origin: https://yuta0032.github.io' '<WORKER>/list?token=dummy' | grep -i access-control-allow-origin`
   → `https://yuta0032.github.io` が返ること。**関係ないオリジンでは返らないこと**も確認
4. **速さと当たり外れの比較（これが本題）**
   **同じ時間帯に**、Worker 経由と GAS 直を **各30回・3秒間隔・`--max-time 30`** で測り、
   9/16 と同じ表（http_code の内訳／所要時間の最小・中央値・最大／3秒超・30秒超の回数／
   JSON でなかった回数）で並べる。**Worker 経由の方が外れが少ないことを数字で確かめる。**
5. **画面**：`WORKER_URL` を入れた `admin.html` を headless で5経路
   （Worker 1回目で成功／Worker 落ち→2回目／Worker 2回だめ→JSONP／forbidden→再ログイン／全部だめ）
6. **本人の実機**：`?v=8` で開いて診断行が **`via=worker res=ok`** になること

**4 を先にやってください。**ここで差が出なければ、Worker を挟む意味がありません。

## 正直な限界

- Google 側が長時間まとめて不調なら、Worker から見ても不調。
  ただしサーバ側で素早くやり直せるので体感は変わるはず
- **Cloudflare → GAS の実際の所要時間と失敗率は未測定。**上の 4 で最初に測る
- Worker 自体が落ちたときは、3本目の GAS 直（JSONP）が保険になる

## 実測の結果（2026-09-16 13:0x、交互に各30回・3秒間隔・--max-time 30）

| | 件数 | http_code の内訳 | 最小 | 中央値 | 最大 | 3秒超 | 30秒超 | 非JSON |
|---|---|---|---|---|---|---|---|---|
| **Worker 経由** | 30 | 200×25、**502×5** | 0.82s | **2.14s** | **16.09s** | 14 | **0** | **0** |
| **GAS 直** | 30 | 200×26、404×1、302×3 | 0.86s | **1.15s** | **30.12s** | 10 | **3** | **4** |

**判定基準（3秒超＋30秒超の合計）：Worker 14 対 GAS直 13 → 基準では不採用。**
`WORKER_URL` は空のままにしてある。

### ただし、失敗の「形」が違う

- **GAS 直**：18回目が `404 / text/html`（16.2秒）、19〜21回目が **30秒で打ち切り**。
  ブラウザから見ると**黙って固まる**種類の失敗。
- **Worker 経由**：失敗は5回すべて **502 を 16.1秒**で返す。**30秒超も非JSON もゼロ。**
  ブラウザから見ると**すぐ次の手に移れる**失敗。

中央値は Worker の方が遅い（2.14s 対 1.15s）。中継のぶん1ホップ増えるので当然。

### 分かったこと：Worker の 8 秒打ち切りが短すぎる

Worker の 502 は5回とも **16.08 秒**＝「1本目 8秒で打ち切り → 2本目と3本目も 8秒で打ち切り」。
一方この時間帯の GAS は **9〜16 秒で返ってくる回が多かった**
（Worker 経由の成功例に 9.0 / 10.9 / 11.3 / 13.1 / 13.6 / 16.1 秒がある）。
つまり **8 秒で切ったせいで、待てば返ってきたはずの応答を捨てている。**

**提案（コードは触っていません。差分だけ出します）**
- `GAS_TIMEOUT_MS` を **8000 → 14000**
- 1本目が駄目なら2本目・3本目を同時、という形は据え置き（最悪 28 秒）
これで 502 の大半は拾えるはず。**変えたら同じ形でもう一度測って、基準で判定し直すのが筋です。**

### 正直な総括

**いまの Worker は採用できません。**基準を満たさないうえ、中央値も悪化します。
ただし**「30秒固まる」「JavaScript でないものが返る」という、画面が黙って死ぬ失敗は消えています。**
そこに価値を見るなら、上の1行を直して測り直す価値はあります。
**この時間帯は GAS 直も 30/30 中 4回が実質失敗**しており、そもそも Google 側が不調でした。
