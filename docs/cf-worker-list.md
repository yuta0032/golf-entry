# 名簿の読み出しを Google の窓口から外す（設計メモ・未実装）

管理画面の一覧が出たり出なかったりする件の根本策。**まだ何も動かしていません。**
デプロイもしていないし、main にも入れていません。

## いま何が起きているか

`admin.html` → GAS の `/exec` → **302 で `script.googleusercontent.com` に転送** → 中身はそちらが返す。
GAS の実行ログは**302 を返した時点で「完了」**になるので、
「GAS は 1.6 秒で完了、ブラウザには届かない」という食い違いが起きる。

- 9/16 の実測（Mac・3秒間隔・30回）：**200 × 30、JSON × 30、中央値 1.05 秒、3秒超ゼロ**
- 一方、責任者の 9/16 9:10 頃の実測では **9回中2回が25秒超**
- 本人の端末では Windows Chrome・LINE 内ブラウザのどちらでも `neterr` / `timeout`
- `script.googleusercontent.com` 自体には**届いている**（本人の回線で Google のページが表示された）

→ **回線やブラウザの問題ではなく、Google 側の当たり外れ**。こちらでは直せない。
だから**その経路を使わない**ようにする。

## 案1：Worker を中継にするだけ（推奨）

```
ブラウザ ──→ Cloudflare Worker ──→ GAS /exec ──→ googleusercontent
         (速い・安定)        (Worker が代わりに踏む。失敗したら即やり直す)
```

- ブラウザは **Cloudflare としか話さない**。Google の当たり外れは Worker が吸収する
- Worker は失敗したら**サーバ側で2〜3回やり直す**。1回あたり数百ミリ秒で、
  利用者は待たされない（ブラウザで待つのと違い、回線の細さに影響されない）
- **KV も押し込みもトリガーも要らない**。GAS は今のまま1文字も変えない
- 名簿は Worker を**通過するだけで保存しない**

### 読み出しの認証（案1・案2・案3で共通）

Worker は LINE に問い合わせて「幹事本人か」を確かめる。GAS の `verifyAdmin` と同じ考え方。

1. ブラウザが `GET /list` に `Authorization: Bearer <LINEのアクセストークン>` を付ける
2. Worker が `https://api.line.me/oauth2/v2.1/verify?access_token=…` を叩き、
   **`client_id` が LIFF のチャネルID（2010392345）と一致するか**を見る
   （※ここを見ないと、**他の LINE アプリのトークンでも通ってしまう**）
3. `https://api.line.me/v2/profile` を Bearer で叩いて `userId` を得る
4. `userId` が幹事の ID と一致すれば通す
5. 検証結果は **10分キャッシュ**（トークンのハッシュを鍵に。生のトークンは鍵にしない）

`id_token` で来た場合は `POST https://api.line.me/oauth2/v2.1/verify`（`id_token` + `client_id`）で `sub` を見る。
`admin.html` は既に両方を持っているので、どちらでも受けられるようにする。

## 案3：押し込み＋KV（ご指定の形。参考）

GAS が書き込み時＋時計トリガーで `{admins, list, updatedAt}` を `POST /push` する。

### push の認証（共有秘密を使わない）

GAS 側で `ScriptApp.getIdentityToken()` を取り、`Authorization: Bearer` に載せる。
Worker 側は Google の JWKS（`https://www.googleapis.com/oauth2/v3/certs`）で署名を確かめ、

- `iss` が `https://accounts.google.com`
- `email` がスクリプト所有者のアドレスと一致（`tagocli7111@gmail.com`。秘密ではないので Worker の変数でよい）
- `email_verified` が true
- `exp` が未来

**★ここに穴が1つあります。** `email` だけを見ると、**別のアプリが同じ Google アカウント向けに
発行した ID トークンでも通ってしまいます**（所有者を騙して別サイトにログインさせれば取れる）。
**`aud`（Apps Script プロジェクトの OAuth クライアントID）も一致させてください。**
クライアントID は秘密ではないので Worker の変数に置けます。ご指定には無かったので明記します。

`appsscript.json` に **`openid` と `https://www.googleapis.com/auth/userinfo.email`** のスコープが要ります。
スコープが増えるので、**所有者の再承認が1回必要**です（前に v54 で避けた件と同じ性質のリスク）。

### 押し込みの頻度

1分ごとの時計トリガーは、**変化が無くても毎分実行枠を使います**。
書き込み時の push を主にして、**時計トリガーは5分ごとの保険**で十分です。

## 「GAS の push は同じ Google の窓口を通るのか」→ **通りません**

`UrlFetchApp.fetch()` は **GAS のサーバから外向きに出る通信**で、
`/exec` → `script.googleusercontent.com` という**中身を配る経路とは無関係**です。
今回問題になっている当たり外れの影響は受けません。
（実際、登録時の LINE 通知とメールは `UrlFetchApp`／`MailApp` で安定して飛んでいます。）

## admin.html 側の変更（どの案でも同じ）

取得の順番を変えるだけ。

```
1本目 Worker（fetch）
2本目 Worker（fetch・並列）
3本目 GAS /exec（いまの JSONP。保険）
```

`LIST_VIA` と URL の組み立てを直すだけで、待ち時間・再ログイン・診断行の作りは今のまま使えます。

### ★ 秘密を人が打つ手順が残るか

**案1なら残りません。** Worker に入れるのは幹事の LINE userId とチャネルID だけで、
**どちらも公開情報**です（userId は既に `admin.html` に、チャネルID は LIFF ID に入っています）。
共有秘密も API キーも作りません。

**案3でも、push の認証に共有秘密は使いません**（ID トークン方式）。
ただし `appsscript.json` のスコープ追加に伴う**再承認は本人の手**が要ります。

唯一残るのは **Cloudflare のログイン**で、これは本人にしかできません。
`wrangler` を使わずダッシュボードだけで完結させれば、**コマンドラインでの `wrangler login` は不要**です。

## 効果の見込みと、正直な限界

- **効く**：ブラウザから見た安定性。Cloudflare は速く、Google の当たり外れは Worker 側で吸収できる
- **効かない場合**：Google 側が長時間まとめて不調なら、Worker から見ても不調。
  ただし Worker はサーバ側で素早くやり直せるので、利用者の体感は大きく改善するはず
- **測っていないこと**：Cloudflare から GAS への実際の所要時間と失敗率。
  作ったら最初に測る（Mac からの 30回と同じ形で）
